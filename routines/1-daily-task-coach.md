# Routine 1: 毎朝のタスク整備コーチ + AI 妥当性レビュー

## 設定

| 項目 | 値 |
|---|---|
| 名前 | 毎朝のタスク整備コーチ |
| モデル | `claude-sonnet-4-5` |
| トリガー | Schedule: Weekdays 09:00（JST） |
| コネクター | ClickUp + Slack |
| 期待効果 | Due Date／Time Estimate 入力率の向上 ＋ 入力値の品質担保 |

## 全体フロー

```
[09:00 起動]
   ├─ Part A: 未整備タスク → 各担当者へ DM (コーチング)
   └─ Part B: 過去24h以内の新規入力 → AI で妥当性レビュー → Hiroko へ DM
```

## 重要：フィールドの厳密な定義

このルーティンが判断に使用するのは **ClickUp の標準フィールドのみ** です。
カスタムフィールドや独自項目は一切参照しません。

| 表記 | ClickUp API フィールド名 | 単位 | 「未入力」の判定 |
|---|---|---|---|
| 期日 | `due_date` | ミリ秒 (Unix timestamp) | `null` または存在しない |
| 見積工数 | `time_estimate` | ミリ秒 (duration) | `null` または `0` |
| 実工数 | `time_spent` | ミリ秒 (duration) | `null` または `0`（Hubstaff 同期） |

「見積工数」「Time Estimate」「Estimate」はすべて同じ `time_estimate` フィールドを指します。
ClickUp UI 上では List View の「Time estimate」列、タスク詳細パネルの「Time estimate」フィールドに表示されています。

## ⚠️ 重要：判定に使うフィールドの厳密な定義

このルーティン全体で「期日」「見積工数」と書いてある箇所は、
すべて ClickUp の標準フィールドを指します。カスタムフィールドや
類似名の項目は一切参照しないこと。

- 「期日」= ClickUp 標準フィールド `due_date`（ミリ秒 Unix timestamp）
- 「見積工数」「Time Estimate」「Estimate」= ClickUp 標準フィールド `time_estimate`
  （ミリ秒 duration。ClickUp UI の「Time estimate」列・フィールド）
- 「実工数」= ClickUp 標準フィールド `time_spent`（Hubstaff が同期するミリ秒 duration）

判定ルール：
- 期日が「入力済み」= `due_date` が `null` ではなく有効な timestamp である
- 見積工数が「入力済み」= `time_estimate` が `null` ではなく、かつ値が `0` より大きい
- ms → h 換算: `hours = time_estimate / 3,600,000`（小数点以下 2 桁まで）

================================================================
# Part A: 未整備タスクのコーチング（メンバー向け DM）
================================================================

## ステップ A-1：未整備タスクの抽出
ClickUp コネクターで以下条件のタスクを取得：
- ステータスが「完了系」（complete / done / closed / cancelled）以外
- 担当者（Assignee）が設定されている
- 以下のいずれかに該当：
  ・`due_date` が `null`（期日が未入力）
  ・`time_estimate` が `null` または `0` 以下（見積工数が未入力）

## ステップ A-2：false-positive ガード（誤検知防止）
抽出した各タスクについて、もう一度 ClickUp から最新データを取得し、
以下を再確認してから DM に含める：
- `time_estimate` が本当に `null` または `0` か（ミリ秒値そのものを確認）
- `due_date` が本当に `null` か

もしいずれかが入力済みだった場合は対象から除外し、
「キャッシュ不整合の可能性あり」とログに記録する。

## ステップ A-3：担当者ごとに集計
担当者別にグルーピング。1 人あたり最大 5 件まで表示、それ以上は「他 N 件」と省略。
各タスクで「不足している項目」を明示する。

## ステップ A-4：Slack DM で本人に通知
各担当者の ClickUp メールから、ステップ 0 のマッピングで Slack メールを特定し、
Slack コネクターで本人に DM を送信。

DM のフォーマット：
---
おはようございます ☀️
ClickUp 上の以下タスクで、*Due date* または *Time estimate* が未入力になっています。
1 日 5 分でも結構ですので、入力をお願いします。

【未整備タスク】
1. [タスク名](ClickUp リンク)
   不足: Due date / Time estimate
2. [タスク名](ClickUp リンク)
   不足: Due date
3. [タスク名](ClickUp リンク)
   不足: Time estimate
（他 N 件）

入力場所:
・*Due date* … ClickUp タスク詳細パネルの「Due date」フィールド
・*Time estimate* … ClickUp タスク詳細パネルの「Time estimate」フィールド
　（List View では「Time estimate」列。8h・2h など時間単位で入力）

入力のお願い:
・期日は「かかる工数」から逆算して設定してください
・工数は 15 分単位の概算でお願いします（例: 0.25h / 0.5h / 1h）
・ブロッカーがあれば、この DM に返信してください

※ 入力された Due date / Time estimate は AI でレビューします。
　不自然な値があった場合はマネージャーから個別にお声がけします。

# Part B: AI 妥当性レビュー（マネージャー向け DM）
================================================================

## ステップ B-1：レビュー対象タスクの取得
ClickUp で過去 24 時間以内に `due_date` または `time_estimate` が
新規追加 or 更新されたタスクを取得（completed 以外）。

判定対象は「`time_estimate` > 0 のもの」のみ（未入力タスクは Part A の管轄）。

## ステップ B-2：類似タスクの参照（Hubstaff 実工数を活用）
各レビュー対象タスクについて、同担当者の直近 90 日間の完了タスクから
タスク名・説明文が類似するものを 3〜5 件抽出し、`time_spent` フィールド
（Hubstaff 同期の実工数。ミリ秒単位）の中央値を算出。
※ 比較対象は `time_spent`（実績）。`time_estimate`（見積）ではない。

## ステップ B-3：妥当性チェック
以下の観点で各タスクを判定（すべて時間換算で評価）：

a) Time estimate の妥当性
   ・🔴 過小: 0.25h 未満、または 類似タスク中央値の 50% 未満
   ・🔴 過大: 8h 超（1 タスクの粒度として大きすぎ → サブタスク分割推奨）
   ・🟡 注意: 類似タスク中央値の 150% 超

b) Due date の妥当性
   ・🔴 当日／翌営業日に設定されているが、同日同担当者の総見積工数が
       1 日稼働時間を超過している
   ・🟡 30 日以上先で、かつ time_estimate が 4h 超（大粒度・遠期日 → 分割推奨）
   ・🟡 過去日付（既に超過）

c) 整合性
   ・🔴 time_estimate に対して due_date までの営業日数が不足
     （例: 工数 16h なのに期日が翌日）

## ステップ B-4：Hiroko へサマリー DM
レビュー結果を Hiroko（hiroko@wasimil.com → Slack マッピング適用）に DM 送信。

DM のフォーマット：
---
🔍 *本日のタスク妥当性レビュー*（過去 24h の入力分）

入力件数: N 件 / 要確認: M 件

【🔴 要確認】
1. [タスク名](URL) — 担当: 〇〇さん
   入力値: Time estimate 0.25h / Due date 2026-05-13
   懸念: 類似タスク中央値 2h との乖離大（過小の可能性）
   推奨アクション: 本人と確認

2. [タスク名](URL) — 担当: △△さん
   入力値: Time estimate 3h / Due date 2026-05-12
   懸念: 同日の総見積 9h が稼働 6h を超過
   推奨アクション: 期日調整 or タスク再配分

【🟡 要観察】
3. [タスク名](URL) — 担当: ××さん
   入力値: Time estimate 5h / Due date 2026-06-30
   懸念: 大粒度＋遠期日。サブタスク分割を推奨

【✅ 妥当】
K 件（明細は省略）
---

要確認・要観察が 0 件の日は「本日の入力 N 件はすべて妥当範囲内」と簡潔に報告。
過去 24h に入力が無い場合は「本日レビュー対象なし」と報告。

# 共通: ログと配慮

## ステップ C-1：実行ログ
- Part A: 通知送信メンバー数、未整備タスク総数、誤検知ガードで除外した件数
- Part B: レビュー対象件数、要確認 / 要観察 / 妥当 の内訳
- マッピング表に該当しない担当者がいた場合は警告ログ
- DM 送信失敗があれば担当者名と理由をログに残す

## 重要な配慮
- メンバー向け DM は催促口調を避け、サポートのトーンを保つ
- ただし「レビューが入る」事実は明示する（自律性に頼り切らない）
- 同じタスクが 3 日連続で未入力の場合のみ、A-4 の DM 末尾に
  「※3 日連続で未入力です」と一言追加
- Hiroko 向け DM の「要確認」は、判定根拠（類似タスクの実績や
  稼働時間との比較数値）を必ず添える
- time_estimate / due_date フィールドへの AI の直接書き込みは行わない
- 推定や指摘はあくまで「提案」「観察」として伝える
- 「見積工数」「Time estimate」「Estimate」はすべて同じ `time_estimate` フィールドを指す。
  別の項目（カスタムフィールド「Goals」や「Points」等）と混同しないこと
